# HitDesign — plan for the MIDI-clip design app (milestones A, B, C)

*Approved direction (2026-07-07): a small design app that takes three MIDI
clips — drums, bass, synths — by drag and drop, plus user-chosen colors, a
dynamics level and a brightness level, and designs a MIDI clip that triggers
hitnotedmx. Length defaults to the drums clip's length, adjustable.*

> **Status: IMPLEMENTED (2026-07-07).** All three milestones landed in the
> **hitnotedmx** repo on branch `claude/pensive-allen-kc62l1` — `design/`
> (GUI-free engine), `design/app/` (the JUCE `HitDesign` app with live rig
> preview), `tools/HitDesignCli.cpp` (the `hitdesign` CLI), wired as two CMake
> targets, guarded by the `design-selftest` CTest. Verified end-to-end:
> real `.mid` in → design → `.mid` out → composed through the real `computeDmx`
> (recipe-render filmstrips), and the GUI launches + lights the rig preview.
> One design refinement vs. the plan below: layering is organised around
> **bass-gated active regions** so a lit stretch always carries the chosen
> colour (never bare white) and rests are truly dark. See the hitnotedmx
> README "HitDesign" section.

## Where it lives, and why

**C++ / JUCE, inside the hitnotedmx repo** — a new `design/` source directory
plus two new CMake targets (`hitdesign` console CLI, `HitDesign` GUI app),
following the exact pattern of the existing `mapping-tool` / `recipe-render`
targets (which already link plugin sources without building the plugin).

Rationale (settled during planning):
- **Zero vocabulary drift.** The app links `TriggerVocabulary`, `Palette.h`,
  `Rig.h`, `Recipes`, `Composition` directly. hitnotedmx's mapping is at
  **v12** while this repo's Python encoder mirrors **v1** — proof that a
  hand-maintained mirror drifts. A linked C++ app is correct by recompilation,
  and the `mapping-frozen` CTest already guards meaning changes.
- **Truthful preview.** The app can call the real `computeDmx` and reuse
  `DmxVisualizer`, so preview (milestone C) is reuse, not reimplementation.
  `recipe-render clip` already plays a `.mid` through `computeDmx` — the
  playback loop for preview exists as reference code.
- **Native UI needs.** `juce::FileDragAndDropTarget` (drop zones),
  `juce::MidiFile` (read/write — `Showcase.cpp` already writes beat-based
  clips with `MidiMessageSequence` + `setTicksPerQuarterNote`).

**This repo (hitdesigndmx, Python) stays the legacy `.als` converter.** Its
IR/looks thinking (beat-flash-not-travel, section coherence, energy signal)
carries over as *design knowledge*, not code. The roadmap Phase 3/4 "looks
library + designer" is superseded by HitDesign for the designer part; the
converter keeps working as-is against mapping v1 clips it already produced.

## Source layout (in hitnotedmx)

```
design/
  MidiClipIO.h/.cpp      read .mid → beat-based NoteList; write NoteList → .mid
  ClipAnalysis.h/.cpp    NoteList → per-role feature sets (drums/bass/synths)
  DesignVocab.h          semantic role → pitch constants (the ONLY place the
                         engine names notes), guarded by a chainName CTest
  DesignEngine.h/.cpp    DesignParams + features → designed NoteList
  app/
    HitDesignApp.cpp     JUCEApplication + MainWindow          (milestone B)
    MainComponent.h/.cpp layout, controls, generate/save        (milestone B)
    DropZone.h/.cpp      per-role file drop target              (milestone B)
    SwatchGrid.h/.cpp    palette picker from vocab::columns()   (milestone B)
    PlaybackEngine.h/.cpp clip player → MidiState → computeDmx  (milestone C)
tools/
  HitDesignCli.cpp       console front-end over DesignEngine    (milestone A)
```

Everything under `design/` except `app/` is GUI-free (links `juce_core` +
`juce_audio_basics` only) so the CLI, the GUI and tests share one engine.

## Milestone A — headless engine + CLI (all the design-quality iteration)

**Deliverable:**

```sh
hitdesign drums.mid [--bass bass.mid] [--synths synths.mid] \
  --colors "Red,Amber" --dynamics 70 --brightness 80 \
  [--bars 8] [--seed 42] -o out.mid
```

Only drums is required; bass/synths refine the design when present. Colors
are named palette entries (case-insensitive prefix match against `Palette.h`
names; `--list-colors` prints them). Output is a beat-based `.mid` (tempo-
agnostic) ready to drop on a HitNoteDmx track.

### A1 — MIDI I/O + fixtures

- `MidiClipIO::read(File) → Clip { notes: {pitch, vel, startBeats, lenBeats},
  lengthBeats }` — merge all tracks, ticks→beats via the file's PPQ, clip
  length = last note-off rounded **up to a whole bar** (4 beats).
- `MidiClipIO::write(NoteList, File)` — same shape as `Showcase.cpp`'s
  writer (one track, `kTpqn` ticks per quarter, matched note-on/off pairs).
- Fixtures: 3 small hand-authored clips (a 4-bar drum groove with a fill, a
  bass line with a quiet half, a sustained pad) generated by a tiny fixture
  writer so they're reproducible, committed as `.mid` under
  `design/fixtures/`.

### A2 — clip analysis (`ClipAnalysis`)

Everything quantized to **1/16** (the convention that worked in the Python
converter). Per role:

- **Drums → rhythm/energy**: onset grid at 1/16 with velocities; per-beat
  energy (velocity sum); overall density; strong-onset mask (top-quartile
  velocity — the "pump" triggers); fill/peak detection (a beat whose density
  is ≫ the clip median → accent moments).
- **Bass → foundation envelope**: per-beat activity in [0,1] (fraction of the
  beat covered by held notes × normalized velocity). Quiet bass = the floor
  light dims/disappears there.
- **Synths → texture profile**: sustain ratio (mean note length / beat),
  chord density, movement rate (pitch-change per bar). Sustained/pad-like →
  breathes; moving/arpy → livelier motion or accent-colour alternation.

### A3 — design engine (`DesignEngine`)

`DesignParams { colors (1–3 palette indices, first = base), dynamics 0–100,
brightness 0–100, lengthBeats, seed }` + the three feature sets → `NoteList`.

Layered output, honoring the composition model's semantics (velocity =
brightness+fade for palette notes; per-recipe tail/speed/density for recipe
notes — semantics table at the top of `Composition.cpp`):

1. **Base wash** — the base palette note held across regions where the bass
   envelope (or drums, if no bass clip) is active; velocity from brightness ×
   local envelope. Darkness = no notes (never blackout note 0 mid-clip).
2. **Beat pump** — re-strike palette notes on drum onsets (the
   beat-flash-not-travel insight): strong onsets fire an accent colour at a
   velocity bump, weak onsets re-strike the base colour. Pump density scales
   with dynamics (low: downbeats only → high: every strong onset).
3. **Motion layer** — chosen deterministically from seed-hashed pools,
   biased by dynamics and the synth profile:
   - low: one held **Breathe** (C1 octave) matching the pad profile;
   - mid: breathe + a beat-locked **Chase** (C0) entering on high-energy bars;
   - high: chase held + **Wild** accents (sparkle/burst — never strobe) fired
     on detected fills/peaks.
4. **Selectors** — default all-lit; at high dynamics, positional
   Left/Right alternation on the backbeat is the only structural motion v1
   allows (no invented travel).
5. **Spots** — warm-white held during calm, pad-heavy stretches at low
   dynamics; otherwise untouched.

Length: default = drums clip length; `--bars` overrides — longer **loops**
the analysis, shorter truncates; every onset/offset snapped to 1/16, nothing
past the clip end. Same inputs + same seed → byte-identical output.

`DesignVocab.h` is the engine's only note-naming point: named constants
(e.g. `kSpotWarmL`, breathe/chase/wild pool arrays, palette octave bases)
each carrying its expected `chainName` string, verified by a new CTest
(`design-vocab`) so a future mapping bump fails loudly instead of silently
emitting wrong notes.

### A verification

- **Eyeball loop:** `recipe-render clip preview.png out.mid` (exists today)
  renders the designed clip through the real `computeDmx` as a filmstrip.
- **CTest `design-smoke`:** generate from the fixtures across a params
  matrix; assert all pitches are in-vocabulary (chainName ≠ "-"), all events
  on the 1/16 grid, no blackout mid-clip, note-on/off balanced, output
  deterministic per seed, and length honored.

## Milestone B — the GUI app

**Deliverable:** `HitDesign.app` (a `juce_add_gui_app` target; builds
cross-platform like the rest of the repo).

- **Three drop zones** (Drums / Bass / Synths): `FileDragAndDropTarget`
  accepting `.mid`; each shows filename + parsed summary (bars, note count,
  a mini onset strip); a clear (✕) button. A file-browser click fallback.
  Drums zone drives the default length.
- **Swatch grid**: built from `vocab::columns()` palette columns + the real
  `Palette.h` colours (24 primary + 12 secondary). Pick up to 3; first pick
  = base, badges show the order. What you pick is exactly what the rig shows.
- **Dynamics + Brightness sliders** (0–100), **Length** field in bars
  (auto-filled from drums, editable), **Seed** number + a **Reroll** die.
- **Generate** runs the engine (fast, synchronous) and enables **Save…**
  plus **drag-out**: `performExternalDragDropOfFiles` of the written `.mid`
  so it drops straight into Live.
- Auto-regenerate on any param change once inputs are present (engine is
  pure + fast), so the app always reflects current settings.
- `PropertiesFile` persistence for last folder, params, window bounds.
- Look and feel: reuse the hitnotedmx editor's styling conventions so the
  family feels consistent.

Verification: build both on macOS and the non-Apple GUI-only path; a manual
script — drop the fixtures, generate, save, load in Live on a HitNoteDmx
track, compare with the `recipe-render` filmstrip.

## Milestone C — preview in the app

### C1 — on-screen rig preview

- `PlaybackEngine`: a ~40 Hz `juce::Timer` stepping the designed clip's
  events through `MidiState` by beat time (BPM field, default 120), calling
  `computeDmx(state, tBeats, vals, grid, 1, 1, &fade, dt)` with a persistent
  `ColorFadeState` (+ `BumpState` if master notes are ever emitted) — the
  same loop `recipe-render clip` runs offline, made real-time.
- Embed **`DmxVisualizer`** (it only needs a `DmxValues&` +
  `SelectionMask&`) under the controls; Play/Stop, loop toggle, a playhead
  strip over the clip. Regenerating while playing hot-swaps the event list.

### C2 — live DMX out (macOS)

- Reuse `EnttecProDmx` exactly as the plugin does: a **Connect USB** button,
  the playback engine pushes each computed frame to the driver at its 40 Hz
  send loop. Off-Apple this stays the existing no-op stub.
- Lets you audition a design on the physical rig with no DAW at all.

## Decisions taken (revisit if wrong)

- Only the drums clip is required; bass/synths optional refiners.
- One app run designs **one section** (per-section workflow), matching the
  section-coherence model; full-song assembly stays in Live.
- Colors are picked from the real palette (no free color wheel in v1).
- Strobe is never auto-emitted; Wild accents cap at sparkle/burst.
- Input currency is `.mid` (Live: File → Export MIDI Clip). Reading
  `.als`/`.alc` directly is a later nicety (port of `als.py`'s gzip-XML
  clip extraction).
- Output is tempo-agnostic (beat-based `.mid`); preview BPM is a preview
  setting only.
